# 🏛 Архитектура SimplCMS: Философия

SimplCMS создавалась как ответ на ограничения классических CMS (WordPress, Joomla, Drupal). 
Наша главная цель — **предсказуемость, скорость, безопасность и контроль версий**.

Ниже описаны 4 столпа, на которых держится архитектура проекта.

---

## 1. Отказ от БД для структуры сайта
Классические CMS хранят вообще всё в базе данных (настройки, страницы, меню). SimplCMS использует **атомарные JSON и PHP файлы**.

**Почему:**
*   **Git-friendly:** Всю структуру сайта (домены, аллиасы, правила URL) можно версионировать. Вы всегда видите, кто и когда изменил маршрут.
*   **Скорость:** Нет накладных расходов на SQL `JOIN` запросы при поиске нужной страницы. Роутер просто читает JSON-файл с диска (а с OPcache это работает мгновенно).
*   **Изоляция ошибок:** Одна опечатка в конфиге ломает только один домен (или страницу), но не роняет всю базу данных.

**Как:**
Структура лежит в `config/site.config` и `.rules.json`. База данных (MariaDB) используется **исключительно для динамического контента** (статьи, пользователи, товары), для которого она и была придумана.

---

## 2. Единый файловый роутер (Tree Engine)
Ранее в проекте сосуществовали два движка: `chain` (цепочка файлов) и `router` (явные маршруты в коде). Это создавало путаницу и баги.

Теперь используется **единый `engine/tree.php`**:
*   Он физически ходит по папкам `algoritm/`. 
*   URL `/ru-ru/blog/post-1` ищет файл `algoritm/lang/blog/slug.php`.
*   Правила маршрутизации (какие URL разрешены, нужна ли авторизация) лежат рядом с файлами в `.rules.json`.

**Почему:**
Это дает **физическое соответствие**: программист всегда знает, где лежит код страницы, просто посмотрев на URL. Это исключает «магию» и скрытые маршруты.

---

## 3. Разделение Конфигураций (Single Responsibility)
Раньше все настройки лежали в одном файле (`cms.config` / `site.config`). Теперь они строго разделены:
*   `engine.config` — настройки самого движка (какой движок рендеринга использовать, включен ли AJAX).
*   `site.config` — данные сети (какие домены обслуживаем, их аллиасы, названия).

**Почему:**
При обновлении ядра CMS (например, переход на новую версию движка) мы меняем `engine.config`, не рискуя затереть структуру доменов.

## 4. UI как ООП (Visuo)
Мы полностью отказались от генерации HTML через конкатенацию строк (`echo '<div>'`) в логике.

Любой HTML генерируется через ООП-билдер **Visuo** (`visuotag` для простых тегов и `visuoel` для сложных компонентов).

**Почему:**
*   **Безопасность (XSS):** Методы `.content()` и `.attr()` по умолчанию экранируют опасные символы.
*   **Переиспользование:** Таблицы, формы, кнопки собираются из готовых классов (`visuoel_form`, `visuoel_table`), что ускоряет разработку и делает интерфейс единообразным.
*   **Тестируемость:** Дерево `visuotag` можно легко проверить тестами, не парся строки.
