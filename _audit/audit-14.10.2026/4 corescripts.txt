# Аудит `corescripts/` — строгий

**Рекомендация по порядку:** делаем **сейчас**. Причина простая — `admin/bootstrap.php` **импортирует команды `corescripts/commands/*` напрямую** (я это видел: `DomainNew::run`, `AlliasNew::run`, `DomainRemove::run`, `AlliasRemove::run`, `PageNew::run`, `FillerNew::run`, `SettingsSet::run`). Значит `corescripts` — **источник**, админка — **потребитель**. Любая дыра в `corescripts` автоматически становится дырой в админке.

Обратное неверно: `corescripts` можно чинить независимо.

Поэтому — сначала строгий аудит слоя, потом админка (которая уже будет отсылать к этому документу).

**Оговорка:** шаблоны `corescripts/templates/*` не смотрю (по твоему указанию). Это влияет на оценку «качество генерируемого кода», но не на архитектуру слоя.

---

## 1. Резюме

`corescripts/` — **самый зрелый слой проекта**. Единый контракт команд, изолированный CLI, атомарная запись конфигов, whitelist-валидация. Это тот слой, на который можно опираться при рефакторинге остального.

**Но** — под поверхностью:
- **Транзакционность отсутствует.** Удаление → потом конфиг, без отката.
- **Хрупкие regex-патчи** `alliasglobal.php` в `BlockNew`.
- **Reflection-хаки** в `DomainRemove`/`AlliasRemove` вместо готового API `Config`.
- **Дублирование** `Template::render` в 4+ командах.
- **Мёртвый API** `plan()` во всех командах.
- **Race conditions** между чтением и записью `.data.json` при параллельных командах.

**Общая оценка: 7.0 / 10.** Хорошо, но с явными «детскими болезнями».

## 2. Архитектура слоя

### 2.1. Схема

```
cli.php                      ← точка входа CLI
  ├── _lib/Cli.php           (ANSI-вывод)
  ├── _lib/Fs.php            (файловые операции)
  ├── _lib/Config.php        (JSON + атомарный save)
  ├── _lib/Validate.php      (валидаторы)
  ├── _lib/Result.php        (DTO)
  ├── _lib/Context.php       (стриминг шагов)
  ├── _lib/Renderer.php      (CLI-рендер Result)
  └── commands/<X>.php       ← 13 команд
        └── run($params, $ctx): Result
```

### 2.2. Контракт команды

```php
class X {
    public static function plan(array $params): array;   // ⚠️ МЁРТВЫЙ
    public static function run(array $params, ?Context $ctx): Result;
}
```

`plan()` — мёртвый. Ни в `cli.php`, ни в `admin/bootstrap.php` **не вызывается**. Это заявка на будущий `--dry-run`, но без реализации.

### 2.3. Единая точка потребления

**Оба интерфейса — CLI и админка — используют одни и те же классы команд.** Это архитектурно правильно:
- бизнес-логика одна;
- интерфейсов два;
- формат ошибок один (`Result`).

**Плюс:** правки в `commands/*` автоматически работают и в вебе, и в CLI.

**Минус:** любая инъекция/race в команде эксплуатируется **и через веб-админку**.

## 3. Безопасность

### 🔴 S-1. КРИТИЧНО. Race conditions при параллельном редактировании `site.config`

**Место:** все команды, которые делают read-modify-write `site.config`.

**Сценарий:**
1. `DomainNew` читает `site.config` (A).
2. `AlliasNew` читает `site.config` (A) — тот же снимок.
3. `DomainNew` модифицирует A → A1 и сохраняет.
4. `AlliasNew` модифицирует A → A2 и сохраняет.

**Результат:** изменения `DomainNew` **теряются**. `Config::save` блокирует файл при записи (`LOCK_EX`), но **не блокирует его между `__construct` и `save`**. Это классический **lost update**.

**Атака/эксплуатация:** через админку достаточно двух одновременных POST-запросов от двух вкладок. Через CLI — двух запущенных процессов.

**CVSS-оценка:** 5.3 (Medium) — порча данных без прямой эскалации.

**Рекомендация:**
- Либо единая точка сериализации (`lock` на `site.config.lock` на время read-modify-write).
- Либо atomic rename через временный файл **с предварительным re-read под тем же локом**.

### 🔴 S-2. КРИТИЧНО. Отсутствие транзакционности при удалении

**Место:** `DomainRemove`, `AlliasRemove`.

**Порядок действий:**
1. `Fs::rmrf($domain_path)` — **удаление файлов**.
2. `Config::save()` — **обновление конфига**.

**Если шаг 2 упадёт** (нет прав, диск переполнен, JSON-ошибка):
- файлы **уже удалены**;
- конфиг **всё ещё указывает** на несуществующий домен/аллиас;
- при следующем запросе движок упадёт в `domain::init()` → `error()` → 500.

**Рекомендация:** обратный порядок (сначала конфиг, потом файлы) **тоже плох**. Правильно — двухфазный commit:
1. Записать конфиг во временный файл.
2. Переместить файлы в `trash/` (не удалять).
3. Атомарно переименовать конфиг.
4. По успеху — `rmrf(trash)`.
5. По ошибке — откатить.

### 🟠 S-3. Существенно. `Cli::ask` не маскирует пароль

**Место:** `Cli::ask`, используется в `AdminPasswd`.

```php
$password = Cli::ask( 'Пароль (введите вручную)' );
```

Пароль **виден в терминале** и остаётся в истории. Команда `admin:passwd` — типичный кейс для `stty -echo`.

**Рекомендация:** отдельный метод `Cli::ask_password()`, использующий `stty -echo` (Unix) / `mode con: ...` (Windows).

### 🟠 S-4. Существенно. `patch_alliasglobal` — regex-инъекция / логическая ошибка

**Место:** `BlockNew::patch_alliasglobal`.

```php
if ( strpos( $content , '$' . $name ) !== false ) return null;
```

Если имя блока `top`, а в файле уже есть `$topbar` — `strpos` найдёт `$top` как подстроку → патч не применится. Ложное срабатывание.

**Обратное:** если имя блока `a`, а в файле есть `$available` — тоже ложное.

**Рекомендация:** проверять через regex с word boundary: `/\$<name>\b/`.

**Дополнительно:** три regex-патча (`property`, `include`, `new`) вставляют код **после последнего совпадения**. Если в `alliasglobal.php` структура изменилась (добавлен комментарий, изменён порядок) — вставка уйдёт не туда. Нет валидации «файл остался валидным PHP» — только lint **после** (в `$lint_errors`).

### 🟠 S-5. Существенно. `Reflection` для обхода приватного `$data`

**Место:** `DomainRemove`, `AlliasRemove`.

```php
$ref = new ReflectionClass($cfg);
$prop = $ref->getProperty('data');
$prop->setAccessible(true);
$prop->setValue($cfg, $data);
```

Работает, но:
- **`Config::removeKeys()`** создан именно для этого и **не используется**.
- `setAccessible(true)` нарушает инкапсуляцию.
- При рефакторинге `Config` (переименование свойства) — молча сломается.

**Рекомендация:** заменить на `$cfg->removeKeys(['domains_real', $domain])` и т.д.

### 🟡 S-6. Средне. `Fs::write` не атомарен

**Место:** `Fs::write()`.

```php
file_put_contents( $path , $content );
```

Не блокирует файл. Параллельная запись может дать **полубитый файл** (часть старого + часть нового).

**Плюс:** команды вызывают `Fs::write` для **новых** файлов (`<block>_<name>.php`), которые ещё не существуют. Race маловероятен.

**Минус:** `PageNew::patch_available_json` **перезаписывает существующий** `.data.json` через `file_put_contents` без лока. Если два пользователя одновременно создают страницы в одном родителе — потеря.

**Рекомендация:** атомарный `write` с `LOCK_EX` + временный файл, как в `Config::save`.

### 🟡 S-7. Средне. `VarsExtract::clean_php` — не поддерживает CRLF

**Место:** `VarsExtract::clean_php`.

```php
'/^\s*public\s+array\s+\$available\s*=\s*\[[^\]]*\]\s*;\s*\n/m'
```

Завершается `\n`, а не `\r\n`. На Windows-файлах с CRLF замены не сработают.

**Плюс:** PHP всё равно кроссплатформенно читает, но `file_get_contents` вернёт `\r\n` — regex не найдёт.

**Дополнительно:** `[^\]]*` не поддерживает вложенные `[]`. Если `$available = [['a','b'],'c']` — сломается.

### 🟡 S-8. Средне. `AdminPasswd` — пароль не подтверждается

**Место:** `AdminPasswd`.

```php
$password = Cli::ask( 'Пароль (введите вручную)' );
```

Нет **двойного ввода**. Если опечатается — потеряет доступ к админке. Обычно запрашивают дважды.

### 🟢 S-9. Хорошо (для баланса)

- **`password_hash`** — правильно.
- **`escapeshellarg`** в `Template::lint` — защита от injection через имя файла.
- **`Validate::skin`** — `basename($skin) === $skin` защищает от path traversal.
- **`Validate::page_path`** — проверки `..`, `//`, leading/trailing `/`.
- **`Validate::domain`** — жёсткий regex.
- **`SettingsSet::WHITELIST`** — явный whitelist + валидация значений.
- **`Config::save`** — атомарная запись + `.bak`.

## 4. Качество кода

### 4.1. Дублирование

| Что | Где | Дубли |
|---|---|---|
| `private static function render()` | `DomainNew`, `AlliasNew`, `PageNew`, `BlockNew`, `FillerNew` | 5 копий |
| `private static function get_domain_ns()` | `AlliasNew`, `PageNew`, `BlockNew`, `FillerNew` | 4 копии |
| `preg_replace_callback('/^( +)/m', ...)` (табы) | `Config::save`, `PageNew::patch_available_json`, `VarsExtract::run` | 3 копии |
| Сборка `$vars = ['domain', 'domain_ns', ...]` | `DomainNew`, `AlliasNew`, `BlockNew` | 3 копии |
| List of BLOCKS | `AlliasNew::BLOCKS`, `AlliasRemove` (hardcoded), `DomainNew::register` (hardcoded) | 3 места |
| Подтверждение удаления | `DomainRemove`, `AlliasRemove` | 2 копии |

**Рекомендация:**
- `Template::render` — использовать везде.
- `Fs::tabs_json_encode()` — вынести общий метод.
- `Blocks::LIST` — константа в одном месте.
- `Cli::confirm_delete()` — общий хелпер для `DomainRemove`/`AlliasRemove`.

### 4.2. Мёртвый код

- **`plan()`** во всех 13 командах — **никогда не вызывается**. Формально API объявлен, документация обещает dry-run, реализации нет.
- `DomainNew::plan` использует `Template::scan(CS_TPL.'/domain')` — если папки нет, вернёт `[]`.
- `FillerNew::plan` возвращает `name`/`block`/`domain`/`allias` — и никто не читает.

**Рекомендация:** либо реализовать `plan()` в `cli.php` (парсить `--dry-run`), либо убрать.

## 5. Производительность

Для CLI — не критично, но админка использует те же команды через HTTP.

| # | Место | Проблема | Влияние |
|---|---|---|---|
| P-1 | `AlliasNew` | `preg_match_all` × 3 в `patch_alliasglobal` + `str_replace` по всему файлу | Medium |
| P-2 | `DomainNew` | `Fs::scan_recursive` + `file_get_contents` + `str_replace` + `Fs::write` × N файлов | Medium |
| P-3 | `FillerNew` | `Template::lint` через `exec('php -l')` для каждого файла | High (web timeout) |
| P-4 | Все команды | `get_domain_ns` читает и парсит `site.config` **многократно** | Low |
| P-5 | `Config::save` | `@copy` в `.bak` + encode + write + flush | Low |

**P-3 — важно.** `Template::lint` для `AlliasNew` запускается до **двадцати раз**: 7 блоков × 2 файла + файлы аллиаса. Каждый — `exec('php -l <file>')`. В CLI это секунды, **в вебе — таймаут** при медленном диске.

**Рекомендация:** для веба — опциональный флаг `--no-lint` или асинхронный lint. Или использовать `php_check_syntax` через отдельный процесс-пул.

## 6. Cross-layer concerns

Поскольку админка **использует те же команды**, эти проблемы касаются и её.

### 6.1. `Context` в веб-контексте

**Место:** `cli.php` создаёт `Context` с callback, который печатает через `Cli::ok/err`. В админке (по логике) должен быть свой callback, пишущий в сессию/JSON.

**Что проверю в админке:**
- есть ли свой `Context` с корректным callback;
- буферизуется ли вывод в вебе;
- что происходит при `exit()` внутри команд — не оборвётся ли рендер.

### 6.2. `Renderer::cli` — только CLI

В админке нужен `WebRenderer` (видел в `admin/_lib/WebRenderer.php`). Контракт должен совпадать — тот же `Result`, разные форматы вывода.

**Что проверю в админке:** как `Result` превращается в HTML/JSON.

### 6.3. `Fs::rel()` — зависимость от `PROJECT_ROOT`

`Fs::rel()` использует `PROJECT_ROOT` — глобальную константу. В CLI определяется в `cli.php`. В админке — в `bootstrap.php`. **Если константа не определена — `str_replace` с пустой строкой сломает вывод.**

**Проверю в админке:** определён ли `PROJECT_ROOT` до вызова команд.

### 6.4. Аутентификация

`corecripts/commands/AdminPasswd` пишет `password_hash` в `site.config.admin`. Но **кто читает** этот хеш? Скорее всего, `admin/_lib/Auth.php`.

**Вопрос:** используется ли тот же `password_verify`, что в `visuo\user`? Или своя реализация?

**Проверю в админке.**

### 6.5. Логика ролей/доступа

`corescripts` **не знает о ролях**. Команды выполняются от имени «того, кто вызвал». В CLI — любой с shell-доступом. В админке — только `admin`, судя по `Auth`.

**Риск:** если в админке будет добавлена роль `editor` с частичными правами, `corescripts/commands/*` не различают роли. `AlliasNew` может быть вызван editor'ом, который не должен создавать аллиасы.

**Рекомендация:** либо команды принимают контекст роли, либо авторизация целиком в админке (что уже так).

## 8. Рекомендации

### 8.1. P0 — немедленно

1. **Сериализовать read-modify-write `site.config`** через отдельный lock-файл.
   ```php
   $lock = fopen(PROJECT_ROOT . '/config/site.config.lock', 'c');
   flock($lock, LOCK_EX);
   // read → modify → save
   flock($lock, LOCK_UN);
   ```
2. **Двухфазное удаление** в `DomainRemove`/`AlliasRemove`:
   - конфиг → temp;
   - файлы → `trash/`;
   - `mv temp config`;
   - `rmrf trash` (по успеху) или `restore` (по ошибке).

### 8.2. P1 — в течение недели

3. **`BlockNew::patch_alliasglobal`** → regex с `\b` + post-lint **до** коммита в файл.
4. **Двойной ввод пароля** в `AdminPasswd` + `stty -echo`.
5. **Откат в `BlockNew`** при неудаче патча: удалить созданные файлы блока.
6. **`VarsExtract::clean_php`** — поддержка CRLF (`\r?\n`) и вложенных массивов.

### 8.3. P2 — в течение месяца

7. **`Config::removeKeys`** вместо Reflection в `DomainRemove`/`AlliasRemove`.
8. **`Template::render`** использовать везде вместо 5 копий.
9. **`Fs::write`** — атомарный через temp + rename.
10. **`PageNew::patch_available_json`** — с `LOCK_EX`.
11. **`Blocks::LIST`** — единая константа.
12. **`Fs::tabs_json_encode()`** — вынести повторяющийся `preg_replace_callback`.

### 8.4. P3 — бэклог

13. **Реализовать `plan()`** как настоящий dry-run: `cli.php --dry-run` вызывает `plan()`, печатает предполагаемые действия.
14. **`Cli::ask_password()`** с маскировкой.
15. **Проверка «последний домен/аллиас»** перед удалением.
16. **Асинхронный/опциональный lint** в web-контексте.

## 9. Оценка по категориям

| Категория | Оценка | Комментарий |
|---|---|---|
| Архитектура | 8/10 | Чистое разделение CLI/lib/commands |
| Читаемость | 7/10 | Единый стиль, но много копипасты |
| Безопасность | 6/10 | Валидация есть, но race + нет откатов |
| Производительность | 7/10 | Для CLI — ок; для web lint тормозит |
