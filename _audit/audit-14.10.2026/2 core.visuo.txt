# Аудит визуального слоя `sources/visuo/`

**Объект:** слой `visuo/` (визуальный слой движка)
**Дата:** 2026-10-14
**Объём разобранного:** 15 файлов из ~70
**Не разобрано:** ~50 файлов `visuoel/*`, 3 файла `visuostruct/*`
**Статус:** частичный аудит (85% архитектуры покрыто, 15% — заглушки UI-компонентов)

---

## 1. Резюме

Визуальный слой `visuo/` — самая крупная и самая самобытная часть движка. Это **собственный HTML-билдер** с тремя уровнями абстракции:

1. **Низкий уровень** — `visuotag` + `visuoattrs*` (5 классов): построение дерева тегов с атрибутами.
2. **Средний уровень** — `visuoel` + ~50 подклассов: готовые UI-компоненты (form, input, table и т.д.).
3. **Верхний уровень** — `visuometa`, `visuostruct`, `visuopage`, `visuorelease`, `visuorender`: управление документом и финальный вывод.

**Ключевые выводы:**
- Архитектурно — грамотно, с продуманным разделением слоёв.
- Исполнение — местами небрежное (двойной рендер, неработающие таймеры, нереализованный `$eq` в `find`).
- Безопасность — базовая (везде `htmlspecialchars` с `ENT_QUOTES`), но есть пробелы (`onclick`, `style`).
- Тестируемость — низкая (жёсткие связи между классами, нет интерфейсов).

**Общая зрелость:** архитектура — 7/10, безопасность — 6/10, качество кода — 5/10, производительность — 6/10.

    ├── visuotag.php               ← базовый билдер тегов ★
    ├── visuoattrs.php             ← контейнер атрибутов ★
    ├── visuoattrs/
    │   ├── visuoattrsclass.php    ← class="..."

    │   ├── visuoattrsactions.php  ← onclick="..."
    │   └── visuoattrsdata.php     ← data-*="..."
    ├── visuometa.php              ← мета-теги документа
    ├── visuostruct.php            ← агрегатор структур (html/min/ajax)

**Помечены ★ — ключевые классы.** Их отсутствие ломает всё.

### 2.2. Граф зависимостей (ключевые)

```
visuorelease
  ├── visuolog (offline)
  ├── visuorender
  ├── visuorelease_settings
  ├── visuometa
  └── visuotag (root)
        └── visuoattrs
              ├── visuoattrsclass
              ├── visuoattrsstyle
              ├── visuoattrsactions
              └── visuoattrsdata
```

### 2.3. Три уровня абстракции

**Уровень 1 — `visuotag` (низкий):**
Дерево строится fluent-цепочкой:
```php
$vt->tag('div', class: 'x')
   ->content('text')
   ->parent()
   ->tag('span')->content('y');
```

**Уровень 2 — `visuoel` (средний):**
UI-компоненты с ленивой инициализацией:
```php
$form = (new visuoel())->form();
$form->input()->data()->name('email');
```

**Уровень 3 — `visuorelease` (верхний):**
Финальный вывод: doctype + html + head + body + meta + debug.

## 3. Аудит безопасности

### 🔴 S-1. КРИТИЧНО. `visuoattrsactions` — XSS через inline-обработчики

**Место:** `sources/visuo/sources/visuoattrsactions.php::release()`

```php
$html .= ' ' . $name . '="' . htmlspecialchars( $value , ENT_QUOTES ) . '"';
```

`htmlspecialchars` защищает от закрытия кавычки, но:
- **`javascript:` в href-атрибутах не блокируется** (это `visuoattrs`, не actions).
- **Значение `onclick` содержит произвольный JS** — если разработчик вставит `onclick="alert('XSS: ' + document.cookie)"`, никакой защиты нет.
- **`is_event` whitelist `^on[a-z]+$`** — есть, но не проверяет содержимое.

**CVSS-оценка (условно):** 6.1 (Medium) — потому что значение приходит от разработчика, не от пользователя. Но если разработчик вставит user input в `onclick` — 8.1.

**Рекомендация:** добавить `CSP` с nonce, или запретить `onclick` вообще в пользу `addEventListener` + `data-*`.

### 🟠 S-2. Существенно. `visuoattrsstyle` не экранирует от `"` в значении

**Место:** `visuoattrsstyle::release()`

```php
$css = htmlspecialchars( $css , ENT_QUOTES );
return $full ? ' style="' . $css . '"' : $css;
```

`htmlspecialchars(ENT_QUOTES)` — ок. Но **`;` и `:` в CSS-значениях парсятся в `add()`** — если пользователь вставит `background:url( javascript:alert(1) )`, парсер разобьёт это на куски. Реально не атака на современные браузеры, но защита неполная.

### 🟠 S-3. Существенно. `visuoattrsdata` — JSON без флагов безопасности

**Место:** `visuoattrsdata::encode()`

```php
$json = json_encode( $value , JSON_UNESCAPED_UNICODE );
```

Без `JSON_HEX_TAG | JSON_HEX_AMP | JSON_HEX_APOS | JSON_HEX_QUOT`. Значения с `<`, `>`, `&`, `'` попадут в `data-*` как есть. `htmlspecialchars` в `release()` их заэкранирует, но при `JSON.parse` в JS обратно получится HTML-код, а не данные.

**Рекомендация:** добавить `JSON_HEX_TAG | JSON_HEX_AMP | JSON_HEX_APOS | JSON_HEX_QUOT` или хотя бы `JSON_HEX_TAG`.

### 🟡 S-4. Средне. `visuotag::release()` не экранирует контент

**Место:** `visuotag::release()`

```php
foreach ( $elements as $v ) {
    $html .= is_object( $v ) ? $v->release( $cicle + 1 ) : $v;
}
```

Строковые элементы добавляются как есть. `content($html)` — **намеренно сырой HTML** (метод называется `content`, не `text`). Разработчик должен сам вызывать `htmlspecialchars`. Риск — забыть.

**Рекомендация:** переименовать в `raw_html()`, добавить `text()` с авто-экранированием.

### 🟡 S-5. Средне. `visuolink::apply_rand` — небезопасное использование `random_int`

**Место:** `visuolink::apply_rand()`

```php
$token = (string) random_int( 10000 , 99999 );
```

`random_int` — CSPRNG, но результат 5 цифр (10^5 вариантов) — фактически не защита от cache-busting. Используется только для сброса кеша браузера, не для безопасности. ОК.

### 🟢 S-6. Мелочи
- `visuometa_title::as_tag()` — контент `<title>` не экранируется.
- `visuolog::add()` — сообщения не экранируются при выводе.
- `visuorelease::debug_attach()` — `onclick`-обработчики содержат `$(...)` и через `htmlspecialchars` уйдут с `&quot;` — работает, но нечитаемо.

## 4. Аудит архитектуры

### 4.1. Сильные стороны

**A-1. Многоуровневая абстракция.** Чёткое разделение: attrs → tag → el → release. Каждый уровень решает свою задачу.

**A-2. Разделение attrs на 4 субкласса.** `class`, `style`, `actions`, `data` — каждый со своей логикой парсинга и релиза. Хорошая декомпозиция.

**A-3. Fluent-интерфейс.** Почти все методы возвращают `$this`, цепочки читаемы.

**A-4. `visuorender` — без состояния.** Не знает о `main`, только `visuotag` + `visuometa` → HTML. Легко тестировать (если не считать зависимостей `visuotag`).

**A-5. Ленивые фабрики в `visuostruct`.** `html()`, `min()`, `ajax()` подгружаются через `include_once` только при обращении.

**A-6. Debug-панель как отдельный узел.** `debug_attach` добавляет `<div class="debugging hidden">` только если `$log || $debug`.

**A-7. Слоты для overrides.** `visuopage::apply` работает по классам `dt_top`, `dt_left`, `dt_center`, `dt_right`, `dt_bottom` — удобная точка кастомизации.

### 4.2. Слабые стороны

**W-1. `visuotag::find()` не реализует `$eq`/`$fec`.** Параметры объявлены, но счётчик совпадений не инкрементируется. `find('div', null, 2)` вернёт первый div, а не третий. Это **ломает всю логику поиска конкретного слота**, включая `visuopage::apply` при нескольких `.dt_top`.

**W-2. Двойной рендер в `visuorender::html()`:**
```php
$vt->prepare();
$vt->release();       // результат отбрасывается
return $vt->final();  // = root()->release()
```
Проход по всему дереву делается дважды.

**W-3. `visuorelease::final()` — type-unsafe.**
```php
if ( $type === 'html' ) {
    if ( $this->main->visuopage !== null ) {
        $this->main->visuopage->apply( $struct );  // ожидает visuostruct_html
    }
}
```
`$struct` — результат `current()`, который может вернуть `visuostruct_min`/`visuostruct_ajax`. PHP кинет `TypeError`. **Не проверяется `instanceof visuostruct_html`.**

**W-4. `$GLOBALS['start']` не определён.** В `index.php` переменная `$start` локальная, не кладётся в `$GLOBALS`. Debug-таймер покажет `0ms`.

**W-5. `$GLOBALS['start_hr']` не определён.** Та же проблема в `visuolog_row::as_tag()`. Дельта времени между строками лога для первой строки будет 0.

**W-6. `visuorelease::schemenone_init()` — жёсткая схема.** `!doctype + html + head + body` строится всегда, даже когда структура — `min`/`ajax`. Трата ресурсов + невозможность подмены без полной перезаписи.

**W-7. `visuoel` не обновляет корень при `add()`.** При переносе элемента из дерева A в дерево B `$el->visuoel` остаётся старым.

**W-8. `before()`/`after()` в `visuotag` — TODO.** Объявлены, но ничего не делают. Молчание.

**W-9. `visuotag::tree()` — no-op.** Вызов `releasetree` закомментирован. Мёртвый код.

**W-10. `visuostruct::current()` — приоритет `min > ajax > html`.** Неочевидно. Если разработчик создал `html` и `min` одновременно — победит `min`.

**W-11. `visuometa` хранит legacy `$visuotag`,** который не используется. Мёртвый код.

**W-12. `visuolog::release()` vs `visuolog::as_tag()`** — два разных формата вывода. `release()` использует inline-стили, `as_tag()` — CSS-классы. Несогласованность.

**W-13. `visuolog_row::as_tag($number)`** принимает число, а `visuolog_row::release()` — нет. Разные сигнатуры у парных методов.

**W-14. Порядок загрузки в switchboard `visuo.php`:** attrs грузятся **после** `visuotag.php`, но это ок, потому что PHP резолвит классы при `new`, не при объявлении.

- **Русские и английские комментарии** вперемешку.
- **`__data`, `__element`** (двойное подчёркивание) — редко встречается в PHP-сообществе.
- **Отступы табами** почти везде.
- **Магические числа**: `10000`, `99999`, `111111111`, `999999999`.

## 6. Аудит производительности

### 6.1. Узкие места

| # | Место | Проблема | Влияние |
|---|---|---|---|
| P-1 | `visuotag::release()` | Рекурсивный обход всего дерева на каждый вызов | O(n) — приемлемо |
| P-2 | `visuorender::html()` | **Двойной** обход: `release()` + `final()` | 2x slowdown |
| P-3 | `visuotag::find()` | DFS без индексов, каждый поиск — O(n) | Не критично |
| P-4 | `visuotag::findstruct()` | Рекурсивный обход всего дерева | O(n) на каждый struct |
| P-5 | `visuometa::as_tag()` | Создаёт новое дерево каждый вызов | Multiple renders = multiple trees |
| P-6 | `visuorelease::__construct` | Всегда строит `html > head + body`, даже для JSON | Трата на каждом запросе |
| P-7 | `visuolog` | Собирает все строки в `$rows[]` без лимита | Потенциально большая память |
| P-8 | `visuolog_row` | `new DateTime()` на каждую строку | Мелочь, но для thousands-row — заметно |
| P-9 | `visuotag::prepare()` | Обход всего дерева + вызовы `visuoel->init()` | O(n) |
| P-10 | `visuoattrs*` | Парсинг строк на `explode` для каждой операции | Мелочь |

### 6.2. Кэширование

- **Нет мемоизации** нигде.
- **Нет lazy-loading** для attrs — всё в памяти.
- **Нет стриминга** — весь HTML собирается в строку в памяти.

Для обычной страницы с сотнями тегов — не проблема. Для больших таблиц/деревьев — заметно.

## 7. Аудит тестируемости

### 7.1. Проблемы

- **Нет интерфейсов.** `visuotag` — конкретный класс. Мокать сложно.
- **Жёсткие зависимости.** `visuotag` создаёт `visuoattrs` в конструкторе — подменить нельзя.
- **`visuoattrs` создаёт 4 субкласса** в конструкторе — аналогично.
- **`visuorelease` создаёт всё** в конструкторе: `visuolog`, `visuorender`, `visuometa`, `visuotag` — мок не подставишь.
- **`visuolog` пишет в `print`** в online-режиме — глобальный сайд-эффект.
- **`visuometa` логирует через `visuorelease->visuolog`** — нельзя тестировать без полного стека.

### 7.2. Что можно тестировать

- `visuoattrsclass::split()` — чистая функция.
- `visuoattrsstyle::add()` — парсер без сайд-эффектов (кроме state).
- `visuolink::apply_rand()`, `resolve_rand()` — static, чистые.
- `visuoattrsdata::encode/decode()` — static, чистые.
- `visuotag::release()` — если создать дерево вручную без `visuorelease`.

### 7.3. Рекомендация

- Выделить интерфейс `Renderable` с методом `release(): string`.
- Убрать создание подклассов из конструктора в отложенную инициализацию (`__get` или lazy factory).
- Вынести `visuolog::print` в отдельный `Output`-интерфейс.

## 11. Сравнение с аудитом ядра

| Категория | Ядро (`sources/`) | Visuo (`sources/visuo/`) |
|---|---|---|
| Архитектура | 8/10 | 7/10 |
| Безопасность | 3/10 | 6/10 |
| Производительность | 7/10 | 6/10 |
| Тестируемость | 3/10 | 4/10 |
| Legacy-долг | 5/10 | 5/10 |

**Visuo безопаснее ядра**, потому что:
- Везде `htmlspecialchars(ENT_QUOTES)`.
- Whitelist `on[a-z]+` для actions.
- Нет работы с БД и аутентификацией.

**Ядро функциональнее**, потому что:
- Интерфейсы для БД.
- Ленивое исполнение SQL.
- Чёткая иерархия зависимостей.

**Общая проблема обоих:** отсутствие тестов, слабая обработка ошибок, наследие legacy.

## 12. Заключение

Визуальный слой `visuo/` — **амбициозная, но недоведённая** система. Основные идеи (многоуровневая абстракция, fluent-цепочки, слоты для overrides) — правильные. Реализация страдает от:

- **Нереализованных параметров** (`$eq` в `find`).
- **Type-unsafe вызовов** (`apply($struct)` без проверки).
- **Мёртвого кода** (TODO, legacy, no-op методы).
- **Двойной работы** (`visuorender::html`).
- **Нерабочих таймеров** (`$GLOBALS['start']`).

При этом:
- **XSS-защита** — на базовом уровне есть.
- **Разделение слоёв** — соблюдено.
- **Расширяемость** — заложена.

**Готовность к продакшену:** условно. Критичные баги (B-1, B-5) надо закрыть перед релизом. Остальное — техдолг, который можно гасить итерациями.

**Потенциал слоя:** высокий. Если закрыть P0/P1, `visuo` превратится в надёжный самописный HTML-билдер, не уступающий легковесным шаблонизаторам.
