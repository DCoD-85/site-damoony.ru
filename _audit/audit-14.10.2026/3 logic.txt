## Достаточно ли для аудита логики?

**Да, для архитектурного аудита — достаточно.** Покрыто:
- База логики: `domain.php`, `algoritm_.php`, `algoritmdata_.php`.
- Домен `damoony.ru`: `allias.php`, `alliasglobal.php`, `alliasscheme.php`, `dataprovider.php`.
- `visuo`: `include.php`, `helpers.php`, `user.php`, `algoritm/*`.
- `alliasglobal`: `alliasblock`, `alliasglobalscript`, `menu`, `top`, filler-механизм, скрипты.
- `alliasscheme`: 5 схем (`min`, `www`, `visuo`, `error`, `login`).

**Не покрыто (для полноты картины, но не критично для аудита):**
- `allias/visuo/dataprovider/` — что делает `$dp`.
- `allias/visuo/algoritm/lang/{docs,news,login,...}/` — конкретные страницы.
- Остальные блоки `left/center/right/bottom/policy/debug`.
- `www`-аллиас целиком (не трогаем).

Аудит можно составить сейчас. Конкретные страницы — отдельным проходом, если понадобится.

# Аудит доменной логики `logic/alpha.0.0/`

**Объект:** слой доменной логики (домен `damoony.ru`, аллиас `visuo`)
**Объём разобранного:** ~25 файлов из ~50+ видимых
**Не разобрано:** конкретные страницы `algoritm/lang/{segment}`, `dataprovider/user`, оставшиеся блоки

---

## 1. Резюме

Доменная логика — **самый сложный слой** проекта. Это симбиоз трёх подсистем:

1. **Роутинг** через `algoritm_` — базовый класс с фреймворком по URL-сегментам.
2. **Блочная система `alliasglobal`** — блоки, скрипты, filler'ы, меню.
3. **Схемы `alliasscheme`** — каркасы HTML для разных типов страниц.

Плюс **переопределение аутентификации** (`visuo\user extends \user`) и **i18n через URL** (`algoritm_lang`).

**Ключевые выводы:**
- **Архитектурно** — интересная, многослойная, местами избыточная система.
- **Исполнение** — рабочее, но с большим объёмом мёртвого кода, дублирования и мелких багов.
- **Безопасность** — `visuo\user` закрывает главные дыры ядра; но CORS-логика в `algoritm::logic()` — критическая дыра.
- **Производительность** — `reload()` схемы делает двойную работу.

**Общая зрелость:** архитектура — 7/10, безопасность — 5/10, качество кода — 4/10.

## 3. Архитектурный анализ

### 3.1. Сильные стороны

**S-1. Многоуровневая маршрутизация.** `algoritm_::include_ext` рекурсивно спускается по URL-сегментам, создавая вложенные алгоритмы. `algoritm_classes[]` хранит историю — можно откатиться.

**S-2. Разделение блока и скрипта.** `alliasblock` (визуальный) vs `alliasglobalscript` (сайд-эффекты). Чистое разделение.

**S-3. Filler-механизм.** `<block>_<allias>.php` рядом с базовым блоком позволяет переопределить вывод для конкретного аллиаса без правки кода.

**S-4. Sections API.** Блок собирается из именованных секций (`section_add`), а не монолитно.

**S-5. `visuo\user`** — современная замена `\user`: `password_hash`, серверные сессии, роли, CSRF, brute-force.

**S-6. i18n через URL.** `headers.php::handle_language` канонично перенаправляет `/` → `/ru-ru/`, `/xx/` → `/ru-ru/`.

**S-7. Схемы как каркасы.** 5 разных схем для разных типов страниц — гибко.

### 3.2. Слабые стороны

**W-1. Тройное дублирование `info`.** `domaininfo`, `alliasinfo` — почти идентичные классы с `name`, `subname`, `history`, `astag()`. Должен быть общий `baseinfo`.

**W-2. Тройная копипаста схем.** `min`, `www`, `visuo` — почти идентичные (`meta/body/init/refresh/load/reload`), отличаются только наборами CSS/JS и слотом `policy`.

**W-3. Двойной источник правды для доступных языков.**
- `main_settings::$langs_available = ['ru-ru','en-en','ch-ch']`.
- `helpers::langs_available()` — тот же массив.
- `alliasglobal_script_headers::$langs_available` — тот же массив.
- `language::__construct` — тот же массив.

**W-4. `algoritm::release()` перезаписывает JSON.**
```php
$this->algoritmdata->set(['([a-z]{2}-[a-z]{2})|lang'], false, true, true);
```
`algoritm.data.json` — мёртвый. Разные `available` в JSON и PHP.

**W-5. `reload()` схемы — двойная работа.** `algoritm::start()` вызывает `load()` и `reload()` последовательно, хотя `reload()` = полный повтор `load()`. Всё дерево строится дважды.

**W-6. `min` схема сломана.** `body()` создаёт только `div.dt_center`, но `visuorelease::visuotag_clear()` стёр `!doctype/html/head/body` от `schemenone_init`. Итог — HTML без обёрток.

**W-7. Три уровня «info» + `algoritmdata_` + `algoritm_classes[]`** — 5 контейнеров состояния. Легко потерять актуальное значение.

**W-8. `dataprovider` дублирует `main->dataprovider` + `current`.** Если `$main->dataprovider` уже есть, зачем нужен `.current`?

## 4. Аудит безопасности

### 🔴 S-1. КРИТИЧНО. CORS через `HTTP_REFERER` + обрезка

**Место:** `algoritm/algoritm.php::logic()`

```php
$referer = $_SERVER['HTTP_REFERER'] ?? '';
$access_origin = '*';
if ($referer !== '') {
    $access_origin = substr($referer, 0, strlen($referer) - 1);
}
header('Access-Control-Allow-Origin: ' . $access_origin);
header('Access-Control-Allow-Credentials: true');
```

**Проблемы:**
- Обрезка последнего символа — бессмысленная и опасная. URL `https://evil.com/x` → `https://evil.com/` (валидный origin!). URL `https://evil.com` → `https://evil.co` (мусор).
- **`Access-Control-Allow-Credentials: true` с произвольным origin** — это позволяет любому сайту делать авторизованные запросы к нашему API и читать ответ.
- `HTTP_REFERER` подделывается через curl/серверные прокси.
- Комбинация `*` + `credentials: true` вообще не работает — браузер отклонит.

**CVSS:** 8.1 (High) — полное нарушение CORS-политики при наличии сессии.

**Правильно:** использовать `HTTP_ORIGIN` + whitelist (как в родительском `algoritm_::logic()`).

### 🟠 S-2. Существенно. `handle_skin()` — XSS через `?skin=`

**Место:** `alliasglobal/script/headers.php`

```php
$skin = $_GET['skin'] ?? '';
if ($skin === '') return;
setcookie('skin', $skin, 0, '/', $url_allias[0] ?? '');
```

- `$skin` **не валидируется**.
- Затем `main_settings::__construct` читает `$_COOKIE['skin']` и передаёт в схемы.
- Схемы используют `$skin` в путях `media/.../skin/<skin>/...`.
- Дальше в `messages::as_tag()` → `<img src="/media/release/<skin>/icons/...">`.

**Риск:** если `$skin` содержит `../../`, путь выйдет за пределы каталога. Или если `<skin>` содержит `"` — потенциальный XSS в атрибуте `src`. Значение идёт через `attrs_add` → `htmlspecialchars`, но проверка всё равно нужна.

**Рекомендация:** whitelist или `preg_match('/^[a-z0-9_-]+$/i', $skin)`.

### 🟠 S-3. Существенно. `?skin=dark&page=2` теряет `page`

**Место:** `headers::handle_skin()`

```php
$href = $link->href($url_domain, $url_base, use_all_adress_data: false);
```

`use_all_adress_data: false` → не наследует `$_GET`. Все остальные GET-параметры теряются при редиректе. То есть `?skin=dark&search=foo` → редирект на `/ru-ru/index/` — потеряли `search=foo`.

### 🟠 S-4. Существенно. `helpers::csrf_token()` с `@session_start()`

```php
if (session_status() !== PHP_SESSION_ACTIVE) {
    @session_start();
}
```

Если сессия закрыта (например, `session_write_close()`) или уже отправлены заголовки — `@session_start()` заглушит warning, но CSRF-токена не будет. Хуже — `csrf_check()` вернёт `false` для всех POST, и всё сломается молча.

### 🟡 S-5. Средне. `algoritm_auth` не выставляет HTTP 401/403

`algoritm_auth::default()` показывает страницу «Вы должны быть зарегистрированы», но код ответа остаётся 200. SEO/мониторинг/браузеры думают, что это нормальная страница.

**Рекомендация:** `http_response_code(401)` (или 403) перед рендером.

### 🟡 S-6. Средне. `algoritm_error` не выставляет 404

Тот же паттерн — визуальная 404 без `http_response_code(404)`.

### 🟡 S-7. Средне. `visuo\user::register` — нет проверки email uniqueness

`$this->dp->exists($login)` — проверка только логина. Два юзера с одинаковым email могут быть созданы, если БД не имеет UNIQUE.

### 🟢 S-8. Мелочи

- `redirect()` в helpers не проверяет `$url` на `javascript:` схему.
- `time_local` проглатывает исключения и возвращает исходный `$utc` — тихая ошибка.
- `visuo\user::authorize()` после `setcookie` вызывает `boot()`, но `$_COOKIE['visuo_sid']` не обновится в текущем запросе — сессия поднимется только со следующего запроса. Из-за этого `$this->current` после authorize всё ещё `null`.

### 5.3. Мёртвый код

- `domain::init()` — `$path = $url_allias[0]` не используется.
- `algoritm_::load_vars()` — никогда не вызывается.
- `algoritm_::clear()` — пустой.
- `algoritm_::debug()` — пустой.
- `algoritmdata_::__construct()` — пусто.
- `algoritm::default()` — пустой.
- `algoritm_error` — `$library`, `$url`, `$url_base`, `$url_vars` не используются.
- `alliasglobal_script_head::$lang` — устанавливается, но не читается.
- `alliasblock::$allias_accepted` — устанавливается, но не используется.
- `domaininfo::ashtml()` / `alliasinfo::ashtml()` — пустые.
- Все `dt_middle` — объявлены, закомментированы в `init()`.
- `refresh($reload)` — параметр не используется.
- `if ($reload == true) { /* всё закомментировано */ }`.
- `algoritm_pageshablon.php` — шаблон для `www`, лежит в `visuo`.

### 5.4. Стиль

- **Fluent-интерфейс** через `! $x ?: $y = ...` — читается плохо.
- **Именованные аргументы** PHP 8 (`class :`, `return :`, `vt :`) — везде.
- **Русские комментарии** вперемешку с английскими.
- **Смешение отступов** — табы и пробелы.
- **Магические числа**: `1000000`, `86400*30`, `9999`, `8` (длина пароля).

## 6. Аудит производительности

| # | Место | Проблема | Влияние |
|---|---|---|---|
| P-1 | `algoritm::start` | `load()` + `reload()` — двойная сборка дерева | Высокое |
| P-2 | `algoritm_::load_data` | `ReflectionClass` + `file_get_contents` на каждый алгоритм | Среднее |
| P-3 | `algoritm_::include_ext` | `include_once` + `class_exists` + `new` — для каждого сегмента | Низкое |
| P-4 | `alliasblock::__construct` | 7 блоков + 2 скрипта создаются всегда, даже если не рендерятся | Среднее |
| P-5 | `alliasglobal::init` | Все блоки в конструкторе — тяжёлая инициализация | Среднее |
| P-6 | `alliasscheme::init` | Все 5 схем создаются, нужна 1 | Среднее |
| P-7 | `refresh()` в схеме | `find(class:)` по всему дереву, O(n) | Низкое |
| P-8 | `meta()` | Хардкод 30+ CSS/JS строк | Низкое (но конфигурируемо) |
| P-9 | `user::boot` | Несколько SQL-запросов (session_find, profile_full, roles) | Низкое |

**Главная проблема:** `algoritm::start()` строит дерево дважды. И `alliasscheme` создаёт 5 схем вместо 1.

## 9. Рекомендации

### 9.1. P0 — немедленно

1. **Убрать CORS-логику из `algoritm::logic()`** или скопировать из родителя (whitelist по `domains_available` + `HTTP_ORIGIN`).

5. **Починить `menu::head()`** — то же.
6. **Валидировать `$skin`** — whitelist или `preg_match`.
7. **Починить `B-13`** — использовать имя группы regex:
   ```php
   // было
   $args[$matches[1]] = $matches[2];
   // стало (для named groups)
   foreach ($matches as $k => $v) if (!is_int($k)) $args[$k] = $v;
   ```

## 12. Заключение

Доменная логика — **амбициозный, но сырой** слой. Он реализует:

- **мультиуровневый роутинг** через классы-алгоритмы;
- **блочную систему** с filler'ами;
- **схемы** под разные типы страниц;
- **современную аутентификацию** (в `visuo`).

**Плюсы:**
- Реальные паттерны (DI, lazy factories, fluent, sections).
- `visuo\user` — правильная замена `\user`.
- `helpers.php` — компактный и полезный.

**Минусы:**
- **Критические баги:** CORS через Referer, `min::body`, `menu::text`, роутер default-ветка.
- **Три копии схем** — 300+ строк на ветер.
- **Мёртвый код** — `load_vars`, `dt_middle`, пустые `ashtml`, неиспользуемые параметры.
- **Неявные конвенции** — URL = имя класса, `_` = глубина.
- **Хрупкие места** — `dirname(__DIR__, 6)`, `static_base[1]` в `algoritm_lang`.

**Готовность к продакшену:** условно. Нужно закрыть P0 (7 пунктов) — тогда можно выпускать. Остальное — техдолг.

**Потенциал:** высокий. Если убрать копипасту и починить 3-4 критических бага, логика станет ядром системы, не уступающим готовым фреймворкам.
